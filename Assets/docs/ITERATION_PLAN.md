# 迭代方案

配套：[游戏设计文档](GDD.md) · [技术方案](TECH_DESIGN.md)

## 0 怎么读这份文档

六个迭代，每个迭代有目标、任务、验收标准、不做的事。验收标准都是可以当场测的，不写"体验良好"这种。

一个迭代的任务数是 7–11 个，规模上大致是"一个人专注做两到三周"。人力和节奏确定后自己乘，这里不折算。

## 1 总览

| 迭代 | 主题 | 做到什么程度 | 任务数 |
|---|---|---|---|
| I0 | 工程基座 | 空场景能跑，Excel 能导进游戏 | 7 |
| I1 | 战斗核心 | 在测试场里能活下来，200 敌人不掉帧 | 11 |
| I2 | 循环闭环 | 能从第一波打到第五波，中途能买东西 | 10 |
| I3 | 内容填充 | 6 角色 10 旅伴 18 道具 2 BOSS 全齐 | 7 |
| I4 | 打磨与交付 | 没玩过的人能自己玩懂 | 7 |
| I5 | 扩展 | buff 系统、无尽、难度 | 4 |

前两个迭代没有玩家看得见的进度，这是正常的。I1 结束时游戏还是"一个灰场里打灰方块"，但它决定了后面所有内容能不能跑起来。

## 2 迭代 0：工程基座

目标：把 v0.1 技术方案里那些"需要先做否则后面返工"的东西一次性配好。

| 编号 | 任务 | 验收 |
|---|---|---|
| I0-1 | 装包：Input System 1.7.0、Cinemachine 2.9.7、Newtonsoft 3.2.1；`activeInputHandler` 改 Both 并重启；三档 Quality 的 URP 配置对齐（阴影、Bloom、MSAA） | Console 无红；切画质视觉不跳变；能打出 Windows 包 |
| I0-2 | 四个场景骨架：Boot / MainMenu / Run / Test_Arena；Run 里放 AppRoot、160×160 地面、方向光、CinemachineBrain + `vcam_Follow`(size 7, rot 50°) | Play 后是 50° 俯视的网格地面，相机跟一个占位胶囊走 |
| I0-3 | asmdef 三层：Game.Runtime / Game.Editor / Game.Tests.EditMode | 改 View 目录下代码只重编 Game.Runtime；Editor 代码不进构建 |
| I0-4 | 事件总线：`IEventBus` + `Channel<T>` + 待发布队列 + 订阅计数 + 退出局内断言归零 | EditMode 测试覆盖订阅、退订、发布顺序、遍历中退订、重复订阅 |
| I0-5 | 配置管线：`Config/GameConfig.xlsx`（8 个 sheet 各 3 行样例）、`tools/export_config.py`（纯标准库解析 xlsx）、校验器、`ConfigDatabase.LoadFrom` | 改一个数 → 跑脚本 → 进游戏日志打出新值；故意写错一个引用 → 脚本非 0 退出并报出"表/行/字段/原因" |
| I0-6 | 输入：`InputActionAsset`（Player + UI 两 Map）、`InputService`、`InputSnapshot` | DebugOverlay 上能实时看到摇杆与按键状态 |
| I0-7 | `DebugOverlay`：FPS、帧时间、GC、配置版本、随机种子 | F1 开关，数值每秒刷新一次 |

退出条件：空场景稳定 60fps；导表全流程能跑通并出错能定位；编译 0 警告；每个任务一次独立提交。

不做：玩法代码、任何美术资源、任何 UI 布局。

## 3 迭代 1：战斗核心

目标：证明"200 个敌人 + 两把武器 + 自写碰撞"这套能跑在 60fps，并且手感过关。

| 编号 | 任务 | 验收 |
|---|---|---|
| I1-1 | 玩家移动：XZ 平面、8 向、无惯性、边界 clamp、相机死区跟随 | 输入到位置变化 ≤ 1 帧；贴着边界跑不穿出去 |
| I1-2 | 冲刺：0.15 秒无敌、CD 2 秒、残影特效占位 | 冲刺能穿过敌人不掉血 |
| I1-3 | `StatBlock` + 三乘区修正 + `RemoveBySource` | 单测：flat/percent/multiply 组合结果与手算一致；移除来源后回到基线 |
| I1-4 | `DamageResolver`：闪避、无敌帧、护甲、暴击、死亡延迟 | 单测：5 种边界（闪避成功、护甲 0、暴击、无敌帧期间、过量伤害） |
| I1-5 | 空间哈希：格子 2 米、32×32、滚动重建、`QueryCircle` / `QueryNearest` | Bench：200 单位 rebuild + 1000 次查询的耗时记录进 `docs/perf-log.md` |
| I1-6 | 敌人追击 AI + 邻格分离力 | 50 个敌人追玩家时不重叠成一坨（能看出是一群不是一个） |
| I1-7 | 弓箭（RangedBehaviour）：索敌、扇形弹道、投射物、穿透 | 射程 8 米内命中，8 米外不开火；穿透数生效 |
| I1-8 | 砍刀（MeleeBehaviour）：扇形判定、伤害窗口、单次挥砍去重 | 一次挥砍对同一敌人只结算一次；攻速翻倍后 DPS 约等于翻倍（误差 < 10%） |
| I1-9 | `UnitView`：几何体 + MaterialPropertyBlock 换色 + 接触阴影盘 + 玩家描边壳 | 200 个敌人渲染无逐对象材质实例（Frame Debugger 确认 SRP Batcher 命中） |
| I1-10 | 命中反馈：闪白、击退、hitstop、Cinemachine Impulse 震屏 | 打中时有可感知的反馈，但连续命中不糊屏 |
| I1-11 | 压力测试 + 预算逐项打表 | 200 敌 + 400 投射物，5 分钟内最低帧率 ≥ 50；模拟 tick ≤ 3ms；GC 0 B/帧 |

退出条件：Test_Arena 里能活满 5 分钟不死（作为压力场景）；性能表所有项达标或已记录偏差原因。

不做：波次、商店、旅伴、UI（除了 DebugOverlay）、真美术。

## 4 迭代 2：循环闭环

目标：从"能打"变成"一局完整的游戏"。数值随便填，但流程必须真实。

| 编号 | 任务 | 验收 |
|---|---|---|
| I2-1 | `RunState` + `RunController`：金币、波次索引、计时、种子、局状态机 | 状态切换日志顺序正确 |
| I2-2 | `WaveController` + Wave 表：刷怪间隔、数量、怪种池、同屏上限、波间商店 | 跑完 5 波，每波时长与 GDD 表一致（±2 秒） |
| I2-3 | 金币掉落 + 磁吸拾取 + 心 | 拾取范围生效；离得远不吸；金币数正确结算 |
| I2-4 | `ShopController`：加权抽卡、去重、保底、价格公式、刷新、买入 | EditMode 跑 10000 次抽卡，品质分布与权重表误差 < 2%；保底 100% 出现 |
| I2-5 | 商店 UI：6 格卡片、价格、刷新、可键盘导航 | 手柄/键盘能完成一次购买，全程不碰鼠标 |
| I2-6 | 旅伴：跟随（无寻路）、武器绑定、重复购买升级 | 4 个旅伴跟随时不重叠、不掉队（超过 4 米瞬移回位） |
| I2-7 | 阵营羁绊：2/4 件触发、失效时回滚 | 卖掉一件凑不成 2 件时属性立刻回退，无残留 |
| I2-8 | 道具系统骨架 + 6 件属性型道具 | 买 3 件同类道具属性叠加正确 |
| I2-9 | HUD：血、金币、波次、CD | 数值变化与 Model 一致，无闪烁 |
| I2-10 | 死亡与结算：死亡 → 结算面板 → 回主菜单 | 中途死亡能正常结算，重开一局状态干净（无残留订阅、无残留实体） |

退出条件：完整打一局 15 分钟不崩；中途死亡重开三次状态正确；商店买东西立即生效。

不做：角色特性、boss、祭坛、旅伴差异化行为（先都是同一种）。

## 5 迭代 3：内容填充

目标：把 GDD 里的内容填满，并做出第一版可玩的平衡。

| 编号 | 任务 | 验收 |
|---|---|---|
| I3-1 | 6 个探梦者特性（含布袋的"不能移动"、咬咬的碰撞流） | 每个角色都能打完 5 波，且打法明显不同 |
| I3-2 | 10 个旅伴的行为差异化 + 4 阵营 | 羁绊组合能影响打法，4 件套不是无脑最优 |
| I3-3 | 18 件道具（含触发型、经济型、特殊型） | 每件道具都能在单局中验证生效（一次性测试用表） |
| I3-4 | 7 种敌人行为（冲锋、抛射、分裂、护盾、精英） | 每种敌人的行为不与另一种混淆 |
| I3-5 | 2 个 BOSS（缝线巨偶、提灯人）+ 动态血量 | BOSS 战时长 40–90 秒，玩家不能秒杀也不能磨 5 分钟 |
| I3-6 | 祭坛：三种献祭 | 献祭后属性立刻变化且不可逆 |
| I3-7 | 数值初调 + 自动化校验（道具价值、成长曲线、经济收支） | 校验脚本能跑；三局不同角色的金币收支落在 GDD 表区间内 |

退出条件：三个角色各跑一局，无 NaN、无卡死、无穿模、无"买了没反应"；一局时长 15–18 分钟。

不做：音频、存档、第二个难度。

## 6 迭代 4：打磨与交付

目标：给没看过设计文档的人玩，他能自己弄明白。

| 编号 | 任务 | 验收 |
|---|---|---|
| I4-1 | 音频：命中、受击、拾取、开火、BOSS、UI 六类，AudioBus 限流 | 连续 50 次命中不出现音量堆叠破音 |
| I4-2 | 打击感细化：不同武器的反馈区分、暴击强调、死亡碎裂 | 闭眼听不出是哪把武器算失败 |
| I4-3 | 结算 UI + DPS 曲线 + 本局统计 | 数据与 DebugOverlay 记录一致 |
| I4-4 | 存档 + 局外解锁（6 个解锁条件） | 杀进程重进，进度还在；删存档能重新开始 |
| I4-5 | 主菜单 + 选人界面 + 暂停菜单 | 手柄能走完全流程 |
| I4-6 | 性能收尾 + Windows 构建 + 构建后冒烟测试 | 包在目标机器上 60fps，无缺失资源 |
| I4-7 | 新手引导：前 90 秒三条提示卡 | 3 个测试者不看说明能撑过第一波 |

退出条件：3 个外部测试者独立完成一局，无人卡在操作或商店。

不做：美术精修（还是几何体）、成就、多语言。

## 8 依赖与关键路径

```
I0-1 包配置 ─┬─ I0-2 场景 ─┬─ I1-1 移动 ─ I1-6 敌人 ─┬─ I1-11 压测
             │             │                          │
I0-5 导表 ───┼─ I0-4 事件 ─┼─ I1-3 属性 ─ I1-4 伤害 ─┼─ I1-7 弓箭
             │             │                          ├─ I1-8 砍刀
             │             └─ I0-6 输入 ─ I1-2 冲刺   │
             │                                        ▼
             └────────────── I2-1 RunState ─ I2-2 波次 ─ I2-4 商店 ─ I2-10 结算
                                                    │
                                                    ▼
                                            I3 全部内容 ─ I3-7 数值 ─ I4 打磨
```

关键路径只有一条：**导表（I0-5）→ 空间哈希（I1-5）→ 波次（I2-2）→ 数值（I3-7）**。这条链上任何一个环节延期，整体一起顺延；其他任务都能并行或挪后。

导表之所以在关键路径上，是因为它决定了后面所有数值内容的填充方式。I0 不把这条管线做通，到 I3 填 18 件道具时会退化成硬编码，之后再改就是大手术。

## 9 每个迭代的门禁

迭代结束时逐条打勾，缺一项不进入下一个迭代：

1. `python tools/export_config.py` 无错误。
2. EditMode 测试全绿，新增逻辑都有测试。
3. 从进游戏到出结算完整手测一遍，无异常日志。
4. 性能数据写入 `docs/perf-log.md`，和上一迭代对比。
5. 每个任务一次提交，提交信息能看出做了什么。
6. 更新对应文档（设计改了改 GDD，结构改了改技术方案）。

## 10 时间不够时砍什么

砍的顺序，从先砍到最后砍：

1. 音频（保留命中、受击、拾取三个音就够）
2. 第二个 BOSS
3. 旅伴 10 → 6（保留每个阵营至少一个）
4. 角色特性 6 → 3（拾荒、布袋、咬咬）
5. 无尽模式与难度 2–5
6. 祭坛

不能砍的四样：导表管线、属性/伤害的单一入口、性能打表、结算流程。这四样砍了之后，项目会以"看起来能跑但数值再也调不动"的形式烂掉。

## 11 防止范围膨胀的清单

以下内容在任何迭代里都不做，除非重新评估：

- 自定义 3D 模型与动画（I4 结束前一律几何体）
- 存档云同步、排行榜
- 成就系统
- 多语言
- 手柄按键自定义
- 联机与回放
- 程序化地图生成
- 装备/稀有度掉落体系（道具就是商店买，不做随机掉落）

后两条是最容易被"顺手加一下"带进来的东西，一旦进来，商店、经济、数值三块都要重做。
